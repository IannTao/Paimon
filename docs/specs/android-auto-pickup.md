## Problem Statement

玩家希望在实体 Android 手机上手动游玩原神时，自动拾取已经出现拾取提示、点击即可获得的物品，减少重复点击。工具必须与原神在同一台手机上独立运行，并在玩家持续移动、转动视角时保持原有触控，不引起停步、摇杆复位或重新落指。

Paimon 当前只有领域与设计文档，没有应用代码、测试基础设施或已完成的真机验证。无障碍服务与 Shizuku 是否能满足真实触控和自动点击共存尚未证明，不能把权限可用等同于输入方案可行。

## Solution

交付自用验证 APK，在 nubia Z50 Ultra、Android 14、MyOS 14.5.33、中文原神上实现本地自动拾取。用户按引导准备无障碍服务、Shizuku 和画面获取授权，进入游戏后明确开启自动拾取，随时通过悬浮按钮暂停。

应用只点击明确识别为物品拾取的提示，无法确认就跳过；对话、开启宝箱、调查与需要攻击的采矿交互均不处理。权限失效、画面获取中断或无法确认游戏画面时停止点击，等待用户恢复。

实施首先验证持续摇杆及摇杆加视角双指操作期间的自动点击能否保留玩家触控。只有该门槛通过，才建设完整识别和配置功能；失败时记录证据并重新讨论输入路径，不降低“不打断移动”的要求。

## User Stories

1. 作为手机原神玩家，我希望辅助与原神运行在同一台实体手机上，以便日常使用不依赖电脑或另一台设备。
2. 作为首版验证用户，我希望获得可安装的自用 APK，以便在基准手机上验证真实使用效果。
3. 作为基准设备用户，我希望应用支持 Android 14 和 MyOS 14.5.33，以便在我的 Z50 Ultra 上运行。
4. 作为中文原神玩家，我希望应用识别中文界面的拾取提示，以便直接使用当前游戏语言。
5. 作为首次使用者，我希望获得必要的无障碍、Shizuku 和画面获取权限引导，以便完成运行准备。
6. 作为玩家，我希望每次新建截图会话时主动确认录屏授权，以便控制画面获取的启动。
7. 作为玩家，我希望应用启动后默认暂停，以便准备权限和进入游戏时不会提前点击。
8. 作为玩家，我希望进入游戏后明确开启自动拾取，以便决定辅助何时开始操作。
9. 作为玩家，我希望通过悬浮按钮随时暂停，以便立即接回完整手动操作。
10. 作为玩家，我希望持续按住摇杆时仍能自动拾取，以便边跑边捡。
11. 作为玩家，我希望移动并转动视角时自动拾取仍保留我的触控，以便正常进行双指操作。
12. 作为玩家，我希望自动点击不会导致停步、摇杆复位或需要重新落指，以便保持连续操作。
13. 作为玩家，我希望只拾取已出现提示且点击即可获得的物品，以便明确辅助的操作范围。
14. 作为玩家，我希望明确识别的物品全部自动拾取，以便首版无需维护物品筛选规则。
15. 作为玩家，我希望无法确认的提示被跳过，以便避免辅助猜测并执行错误操作。
16. 作为玩家，我希望辅助不会误点 NPC 对话，以便不会被意外带入对话流程。
17. 作为玩家，我希望辅助不会自动开启宝箱或执行调查，以便这些交互仍由我决定。
18. 作为玩家，我希望辅助不会为采矿执行攻击，以便首版保持直接拾取的操作边界。
19. 作为玩家，我希望权限失效后停止点击，以便辅助不会在失去运行条件后继续操作。
20. 作为玩家，我希望截图中断或会话结束后停止点击，以便不会依据失效画面继续操作。
21. 作为玩家，我希望无法确认游戏画面时停止点击，以便辅助不会对其他画面执行拾取操作。
22. 作为玩家，我希望异常后等待我恢复运行，以便我能重新确认权限和游戏状态。
23. 作为玩家，我希望日常识别和决策完全在手机本地完成，以便运行不依赖网络。
24. 作为玩家，我希望默认不保存游戏截图，以便避免持续占用存储。
25. 作为验证用户，我希望主动开启诊断时能够保存必要截图，以便排查识别问题。
26. 作为验证用户，我希望首版固定游戏显示设置和横屏方向，以便能够复现实验条件。
27. 作为验证用户，我希望通过连续运行和人工标注评估拾取效果，以便确认成功率和误触情况。
28. 作为玩家，我希望成功拾取能及时触发点击，以便减少等待。
29. 作为玩家，我希望辅助对游戏帧率的影响有明确验收目标，以便保持游戏流畅度。
30. 作为验证用户，我希望不可测量的指标被明确标为未验证，以便不会把缺少证据当作通过。
31. 作为项目所有者，我希望先验证触控共存再投入完整功能，以便尽早发现会阻断核心体验的问题。

## Implementation Decisions

- 采用同一台实体 Android 手机独立运行的形态，Rust 实现核心，允许 Kotlin 接入 Android 平台能力；不要求纯 Rust 应用。
- 权限方案为无障碍服务与 Shizuku。不将 Root 作为既定方案，不以电脑或另一台设备参与日常运行作为解决办法。
- 游戏交互限定为屏幕观察、目标识别和 Android 系统输入。不读取或修改游戏内存，不修改游戏文件；后续跑图采集和自动战斗同样遵守该边界。
- 在实现完整识别前，优先验证真实触控与注入点击共存。无障碍手势派发存在取消正在进行手势的已知约束；Shizuku 提供身份与系统能力接入，不承诺触点合流。
- 输入 API、识别算法与依赖、Rust/Kotlin 接口和界面框架尚未选定。实现不得将尚未验证的技术选项写成已经证明可行的决策。
- 核心职责覆盖画面处理、拾取提示识别和拾取决策；Android 平台接入覆盖画面获取、授权、系统输入、运行生命周期和用户控制。具体模块划分在触控验证后确定，不预先建立多套测试接口。
- 采用 MediaProjection 获取画面时，每次新建会话由用户手动确认录屏授权。截图会话结束后停止拾取，等待用户重新启动。
- 产品行为区分暂停与运行：启动默认暂停，用户明确开启后才允许拾取；暂停、权限失效、画面中断或无法确认游戏画面时不再执行点击。恢复由用户触发。
- 只对明确识别的拾取提示执行点击；未知提示跳过。首版不提供物品黑白名单。
- 固定一套游戏显示设置和横屏方向，实际配置在真机验证时记录，不预设未经验证的分辨率、缩放或画质参数。
- 日常识别与决策完全本地完成，默认不保存截图；仅用户主动开启诊断时保存必要截图。具体截图保留策略未在本次讨论中确定。
- 不新增已指定的服务器、数据库或远端 API 合同；首版没有此类已确认需求。

## Testing Decisions

- **测试边界提案，待用户确认：**以完整“自动拾取会话”为一个主要行为测试边界。从外部提供画面、用户启停、授权及会话状态变化，观察是否点击、点击目标和时机，以及游戏侧的拾取结果和真实触控连续性；不围绕内部函数、算法实现或模块调用顺序编写镜像测试。
- 该边界覆盖 Rust 核心与 Kotlin 平台接入组成的完整拾取行为，包括画面识别、操作决策、启停与异常处理。平台替身可用于可重复的识别及状态场景，但不能证明真实输入共存成立。
- 真机测试使用真实 Android 输入路径及原神游戏结果，验证持续摇杆和摇杆加视角双指操作；不能以模拟输入接收器或单次点击成功替代。
- 仓库目前没有应用代码、既有测试边界、相似测试或测试框架可复用。具体测试工具在实现时选定，以外部行为和可观察结果为标准。
- 首个技术门槛须记录设备及系统版本、输入方式、游戏显示配置，以及是否停步、摇杆复位、触点取消、需要重新落指或点击被忽略。失败则停止完整功能推进，记录结果并重新讨论输入路径。
- 验证明确物品提示会被拾取；未知提示、对话、宝箱、调查和需要攻击的采矿交互不会被误点。暂停、权限失效、截图中断和无法确认游戏画面的场景均须验证停止点击。
- 验证应用启动默认暂停、用户明确开启与悬浮暂停，以及画面会话结束后等待用户恢复的行为。
- 验证日常运行不依赖网络、默认不保存截图，仅主动开启诊断时保存必要截图。
- 真机连续运行至少 30 分钟，覆盖边移动、边转视角、连续拾取；自动点击造成的移动中断、需要重新落指以及误点非拾取交互均为 **0 次**。
- 人工标注至少 **100 次**符合首版范围且提示清晰可见的拾取机会，成功拾取比例至少 **95%**。漏识别及因无法确认而跳过都计入未成功拾取。
- 在成功拾取样本中，至少 **95%** 从清晰拾取提示出现到触发点击不超过 **1 秒**；该指标不代替整体拾取成功率指标。
- 固定游戏设置，在相同场景对照开启与关闭辅助时的平均帧率，开启后的下降不超过 **10%**。同时记录功耗和温度，暂不设数值门槛。
- 上述均为验收目标，当前没有已完成的实现或测量证据。测量条件不足的指标标为未验证，不判为通过。

## Out of Scope

- 跑图采集、自动战斗及其他 BetterGI 能力的具体实现。
- BetterGI 脚本、路线和配置格式兼容；未来路线兼容性另行讨论。
- 对话、开启宝箱、调查、通过攻击采矿及其他非直接拾取交互。
- 物品黑白名单。
- 任意设备、Android 版本、游戏语言、横屏方向、显示布局和 UI 缩放的自动适配。
- 公开发布、应用商店上架、更新机制和广泛机型支持。
- 云端识别、日常联网依赖、默认持续保存截图。
- 游戏内存读写、游戏文件修改，以及未获确认的 Root 或外部设备控制替代方案。
- 在触控共存失败时将“松手再拾取”作为自动降级，或以降低不打断移动要求换取交付。

## Further Notes

本规格综合本次设计访谈中逐项接受的结论，不代表应用已实现或真机验证已通过。发布到本地 Markdown issue tracker 时使用 `Status: ready-for-agent`，含义是实现范围已明确，而非平台可行性已经证明；实施顺序必须保留首个技术门槛。测试边界仍待确认，当前文件为规格草稿。

后续功能推进顺序为自动拾取、跑图采集、自动战斗。本规格只覆盖首版自动拾取，后两阶段需要独立细化。
