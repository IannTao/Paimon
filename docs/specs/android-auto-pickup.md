# Android 全自动跑图采集规格

**Status:** ready-for-agent

## Problem Statement

玩家希望在实体 Android 手机上，让 Paimon 独立完成跑图到资源点、调整视角和拾取，任务执行期间不进行任何手工游戏操作。仅在玩家移动和转视角时补充自动点击，无法满足这一目标；要求玩家在卡住、识别失败或到达下一资源点时接管，同样不符合全自动采集的预期。

2026-10-30，用户进一步要求先兼容 BetterGI repo/pathing 的路径点，再基于这些路径点实现跑图与拾取。原“首版排除路线格式兼容”的范围由此取代，后续功能不能先依赖另录一套 Paimon 专用点位。

本规格发布时，已有实现是有限次数坐标点击的触控验证原型，另有独立输入 helper。它们尚不具备基于屏幕的定位、自动导航、拾取识别和采集任务闭环。旧方案的真实触控共存验证结论不能作为全自动采集已可行或不可行的结论。

## Solution

交付在同一台手机上与原神独立运行的自用 APK。完成安装、系统授权和任务准备后，玩家启动一次采集任务，Paimon 自行检查运行条件、观察画面、移动到资源点、调整位置和视角、识别并点击拾取提示、确认取得物品，并推进到后续资源点，直到任务完成。

用户先将 BetterGI 路线原文件导入手机，应用预览有序路径点并检查整条路线所需能力；支持齐备后从屏幕定位，以相同游戏坐标系执行传送、按点移动和到点拾取。任务不依赖玩家运行中提供位置、控制摇杆、转动视角、点击拾取或手工脱困。短暂异常由程序有限恢复，无法恢复则释放输入并结束。开发先完成导入和预检，再完成坐标定位、基础按点移动及自动传送，随后验证短路线完整闭环并扩展连续采集。

## User Stories

1. 作为手机原神玩家，我希望 Paimon 与原神在同一台实体手机上运行，以便日常采集不依赖电脑或另一台控制设备。
2. 作为玩家，我希望日常识别和决策在手机本地完成，以便任务执行不依赖网络服务。
3. 作为首版验证用户，我希望获得可安装的自用 APK，以便在基准手机上实际验证。
4. 作为基准设备用户，我希望应用适用于 nubia Z50 Ultra 的 Android 14、MyOS 14.5.33 环境，以便验证与我的设备一致。
5. 作为中文原神玩家，我希望应用识别中文拾取提示，以便使用现有游戏语言。
6. 作为首次使用者，我希望应用提供必要的权限和画面获取准备引导，以便启动前完成运行准备。
7. 作为玩家，我希望程序启动后默认空闲，以便未选择并启动任务时不会操作游戏。
8. 作为玩家，我希望一次启动即可连续执行采集任务，以便无需逐个资源点确认。
9. 作为玩家，我希望启动前检查权限、游戏前台状态和画面获取能力，以便条件不足时不会盲目操作。
10. 作为玩家，我希望程序检查约定的起点条件，以便不会从无法确认的位置开始导航。
11. 作为玩家，我希望程序从画面判断当前位置或导航参照，以便无需运行中手动标记位置。
12. 作为玩家，我希望程序自动控制移动方向，以便无需手动按住摇杆。
13. 作为玩家，我希望程序根据实际移动反馈修正方向，以便不会仅按预定时长盲走。
14. 作为玩家，我希望程序自动调整视角，以便无需手动寻找资源和拾取提示。
15. 作为玩家，我希望程序确认到达资源点，以便不会将输入完成误认为实际到达。
16. 作为玩家，我希望程序在资源点附近调整位置和视角，以便让可拾取资源进入交互范围。
17. 作为玩家，我希望程序只点击明确识别的拾取提示，以便不会猜测未知交互。
18. 作为玩家，我希望明确识别的直接拾取物品都被自动拾取，以便首版无需维护物品筛选规则。
19. 作为玩家，我希望程序确认取得物品的结果，以便不会把命令执行成功当成采集成功。
20. 作为玩家，我希望程序不只依据拾取提示消失就判断成功，以便减少视角变化或移动造成的误判。
21. 作为玩家，我希望当前资源点处理后自动推进下一资源点，以便完成连续采集。
22. 作为玩家，我希望所有目标处理后程序结束任务，以便不会在完成后继续操作。
23. 作为玩家，我希望程序不误点 NPC 对话，以便不会意外进入对话流程。
24. 作为玩家，我希望程序不自动开启宝箱或执行调查，以便首版保持直接拾取的明确范围。
25. 作为玩家，我希望首版不通过攻击采矿或战斗取得资源，以便任务范围与已确认能力一致。
26. 作为玩家，我希望短暂画面不确定时程序有限重新观察，以便无需我手动处理暂态问题。
27. 作为玩家，我希望未发现资源时程序有限调整视角或重新定位，以便不立即要求我介入。
28. 作为玩家，我希望移动无进展时程序有限尝试恢复，以便无需手工脱困。
29. 作为玩家，我希望无法确认位置时停止盲目前进，以便避免持续偏离路线。
30. 作为玩家，我希望恢复超过上限后任务明确失败，以便不会无限重试或等待我接管。
31. 作为玩家，我希望权限失效时停止任务，以便程序不会在运行条件不足时继续操作。
32. 作为玩家，我希望截图中断时停止任务，以便不会依据失效画面继续导航和点击。
33. 作为玩家，我希望离开游戏或锁屏时停止任务，以便不会对其他画面执行采集操作。
34. 作为玩家，我希望任何结束路径都释放可控输入，以便不会残留摇杆按住或视角拖动。
35. 作为玩家，我希望随时可以主动停止任务，以便立即终止自动操作。
36. 作为玩家，我希望停止后的迟到画面或输入回执不会重启任务，以便停止决定持续有效。
37. 作为玩家，我希望需要重新授权的中断结束当前任务，以便不会把我的补操作掩盖为全自动成功。
38. 作为验证用户，我希望结果区分成功、失败和主动停止，以便准确判断完成情况。
39. 作为验证用户，我希望记录资源点进度、恢复次数和停止原因，以便定位未完成任务的问题。
40. 作为玩家，我希望默认不保存截图，以便避免日常运行持续占用存储。
41. 作为验证用户，我希望主动开启诊断后可保存必要画面，以便事后复核识别和导航问题。
42. 作为验证用户，我希望固定横屏方向和游戏显示设置，以便重复同一验证条件。
43. 作为验证用户，我希望完整任务执行期间玩家游戏操作为零，以便验证确实满足全自动要求。
44. 作为验证用户，我希望人工补操作的任务被记为失败，以便不夸大自动完成能力。
45. 作为验证用户，我希望缺少证据的结果明确标为未验证，以便不会把未知当作成功。
46. 作为项目所有者，我希望先验证单资源点完整闭环，以便尽早发现画面、导航或输入能力的关键阻塞。
47. 作为验证用户，我希望记录完成时长、帧率、温度和功耗，以便评估完整任务的运行成本。
48. 作为玩家，我希望直接导入指定 BetterGI 路径点仓库的路线文件，以便复用已有路线而无需重新录点。
49. 作为玩家，我希望预览路线名称、地图和点位顺序，以便执行前了解任务内容。
50. 作为玩家，我希望导入保留游戏坐标、点位类型、移动模式、动作和参数，以便不会改变原路线要求。
51. 作为玩家，我希望整条路线在启动前检查必需能力，以便不会运行到一半才发现动作不支持。
52. 作为玩家，我希望合法但暂不支持执行的路线仍可预览并说明缺失能力，以便区分文件错误与能力未完成。
53. 作为玩家，我希望手机定位能对应路线使用的游戏坐标，以便程序能实际朝路径点行进。
54. 作为玩家，我希望程序自动完成路线所需的传送并确认结果，以便无需在任务中补做起点操作。
55. 作为玩家，我希望途经、精确目标和朝向点按各自含义执行，以便不会把所有点当成同一种移动目标。
56. 作为玩家，我希望相同坐标上的不同动作和原始点位顺序得到保留，以便不因去重或排序破坏路线。
57. 作为玩家，我希望未知地图、移动模式或动作不会被静默替换或跳过，以便不会错误宣称整条路线已完成。
58. 作为玩家，我希望已导入的路线能离线执行，以便运行过程不依赖实时下载或远端调度。

## Implementation Decisions

- 保持同机独立运行的架构，Rust 实现核心，Kotlin 接入 Android 平台能力；不要求纯 Rust 应用。
- 按 ADR 0004 优先建立 BetterGI 原格式的导入、预览和整条路线能力预检，之后实现游戏坐标定位、按点移动与自动传送，再接入拾取和完整采集。07 保留为已验证的底层能力，08 改为路线目标点驱动；新增前置工单不重编已有编号。
- 路线数据兼容与执行兼容分开记录。保留元数据、浮点游戏坐标、数组顺序、重复位置和动作参数；原始 id 不作为重排依据，不把路径点变成屏幕像素或将所有 target 视作物品。
- 固定上游仓库提交和真实样本，兼容 snake_case 及已核查的缺省规则，识别注释和尾随逗号。缺失/非法/非有限坐标和空点列拒绝进入执行；未知行为或执行相关配置未支持时整条路线不可启动，不自动删点、降级或截断。展示性扩展元数据保留，不无差别拒绝所有新增字段。
- 首批执行范围针对 Teyvat 基础地面路线，识别 path、target、orientation 和 teleport 的区别。自动传送纳入基础执行；其他移动模式、动作与地图逐项扩展，不能把解析成功视为其已实现。上游版本号作为格式与能力核查信息，不与 Paimon 版本号直接比较。
- 屏幕定位必须建立到游戏坐标的映射及可信状态；07 局部小地图位移不等于绝对定位。未知位置或地图时不盲走，传送后重新确认位置，后续输入持续依据屏幕反馈校正。
- 遵守 ADR 0002 的屏幕观察与 Android 系统输入边界，不读写游戏内存，不修改游戏文件。ADR 0003 取代 ADR 0001 中手动游玩下的自动拾取优先顺序和真实触控共存门槛；其余运行形态与语言决定继续有效。
- 沿用无障碍服务与 Shizuku 的权限方向，不将 Root、电脑或外部设备日常控制作为替代方案。权限身份可用不等于输入能力已验证。
- 程序统一协调移动、视角和拾取。平台输入能力必须支持实际游戏所需的按住、移动、点击和释放；是否需要多个合成触点由真机操作验证决定，不预设物理触控代理 helper 为必选路径。
- 核心承担画面处理、拾取提示识别、定位与进度判断、任务决策和有界恢复；平台层承担权限、画面获取、输入执行与释放、前台与生命周期监控、用户停止和诊断持久化。具体接口随闭环原型确定，不提前引入多套测试接口。
- 完整任务以准备检查、定位与进度判断、自动移动、到点对准、拾取确认、推进或结束形成闭环。动作必须由后续屏幕观察校正，固定坐标或固定时长操作仅能用于能力探测，不能独立证明自动采集可用。
- 程序启动默认空闲；完成任务准备并明确启动后自行推进，不逐点要求玩家确认。保留主动停止入口，停止后的异步结果不能重新驱动任务。
- 准备检查覆盖权限、画面获取、前台游戏、屏幕配置和约定起点条件；检查失败不发出游戏操作并报告原因。
- 仅处理明确的直接拾取提示。未知提示跳过，不因识别不确定而尝试对话、开启宝箱、调查、攻击采矿或战斗。首版不提供物品黑白名单。
- 到点和拾取结果必须有画面证据；命令返回成功不能证明游戏接受输入或取得物品，拾取提示消失不能单独作为成功证据。
- 对短暂画面不确定、资源未发现和移动无进展，采取有次数或时间上限的重新观察、视角调整或重新定位。无法确认进度时停止盲目前进，超过上限则结束任务；不得无限重试或将人工接管作为恢复步骤。
- 权限失效、截图会话结束、离开游戏或锁屏时停止当前任务并释放可控输入；所有正常完成、失败和主动停止路径都需要释放输入。需要重新准备后启动的执行视为新任务。
- 安装、系统授权和任务选择属于执行前准备。沿用原方案的系统授权约束，若采用 MediaProjection，则在任务开始前完成录屏授权；不假定 Shizuku 能绕过确认或自动重建截图会话。
- 首版固定基准设备、中文界面和一套横屏游戏显示设置，实际配置随真机验证记录。不把广泛适配作为首版目标。
- 默认不保存截图，只有主动启用诊断时保存必要画面；记录任务结果、资源点进度、恢复次数和停止原因。截图保留策略未定。
- 从指定仓库选择不要求战斗或范围外交互的真实短路线，先完成导入、定位、按点移动与传送，再验证单资源点闭环和连续资源点。外部路线表达沿用 BetterGI 原文件；定位方法、成功证据、恢复上限和验收阈值在原型中落实，不虚构已确认值。
- 不新增服务器、数据库或远端 API 合同；路线数据合同采用用户指定的 BetterGI 路径点格式及已核查基线，不另造一套外部录点格式。

## Testing Decisions

- **已由用户确认的主要测试边界：一次完整采集任务。** 从应用或公开任务入口提供任务准备、启动与停止，以及画面、时间、授权和前台等外部条件变化；观察发出的游戏输入、资源点推进、恢复终止、任务结果和输入释放。测试穿过画面理解、任务决策与平台适配的协作，不单独为每个内部模块建立镜像测试边界。
- 将路线原文件导入和预检作为任务准备行为，从应用入口验证预览、点位顺序与重复位置保留、坐标精度、元数据及动作参数、缺省规则、合法但不可执行报告，以及错误输入不发出游戏操作；不以内部解析函数通过代替兼容验收。
- 用固定提交的真实路线建立回归集合：基础传送+walk+path/target 样本用于主线，含 fly/stop_flying 的样本用于未实现能力拒绝测试。覆盖缺失坐标、非有限值、未知动作/地图和执行配置；定位、传送与整条采集分别需要真实屏幕和游戏结果证据。
- 优先沿用现有公开会话接口测试外部行为的做法，将有限坐标点击会话扩展或替换为采集任务入口；现有接口只能表达启动、轮询动作、命令回执和停止，尚不能承载画面驱动的完整任务。需要的新增接口在完整任务层提出，不固定内部函数或状态机形状。
- 可重复的场景使用画面序列、可控时间和平台状态替身，验证实际发出的输入和最终结果；不能只提供已识别的资源点标签来代替对画面识别行为的覆盖，也不围绕算法调用次数或内部调用顺序断言。
- 既有 Rust 会话行为测试覆盖有界执行、慢命令不积压、停止后迟到回执不重启、命令失败和超时，可复用这些行为场景与测试风格。独立 helper 已有输入流与 watchdog 测试，但它们不能证明画面识别、导航、原神接受输入或完整采集成功。
- 同一个任务行为合同在基准真机上使用真实画面获取、真实 Android 输入路径和游戏结果验证，覆盖 Rust 核心与 Kotlin 平台接入；平台替身不能替代真机证据。触控接收器或单次点击成功不能作为完整闭环通过条件。
- 首个技术门槛：从约定起点无人触控完成一次观察画面、移动到资源点、调整视角、拾取、确认结果的闭环，结束或异常时可靠释放输入。无需先证明真实手指和合成触点共存。
- 完整路线场景验证连续资源点推进和全部完成；成功要求有实际到点与取得物品的证据。资源缺失或未确认时保留相应结果，不将跳过默认为采集成功。
- 异常场景覆盖未知或非拾取提示、画面不确定、位置不确定、移动无进展、资源未发现、输入失败、权限失效、截图中断、切离游戏、锁屏和主动停止；检查有界恢复、停止后无新增操作、释放可控输入，以及迟到回执不复活任务。
- 成功任务的运行中玩家游戏操作必须为 0 次；手动标点、移动、转视角、点击或脱困均使该次任务不能判为自动成功。人工在执行后复核或标注证据不属于运行中介入。
- 误点对话、宝箱、调查等范围外交互的验收目标为 0 次。记录完成率、任务耗时、帧率、温度和功耗，短路线确定后再设重复次数与数值阈值；旧手动游玩拾取指标不自动沿用。
- 验证日常执行不依赖网络、默认不保存截图、主动启用诊断才保存必要画面，以及报告区分成功、失败、主动停止和未验证证据。
- 真机记录设备、系统、游戏显示配置、起点和路线、输入及截图路径、任务结果和恢复情况。缺少证据的指标标为未验证；发布规格不等于可行性门槛已经通过。
