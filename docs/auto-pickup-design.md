# 自动拾取设计

本文件记录设计访谈中已经确认的首版范围。运行形态和实现语言见 [ADR 0001](adr/0001-standalone-android-with-rust-core.md)，领域术语见 [术语表](../GLOSSARY.md)。未确认项不视为实现要求。

各项决策已逐轮确认，整体设计基线待用户最终确认。本文不表示实现或真机验证已经完成。

## 验证基准

- 设备：nubia Z50 Ultra。
- 系统：Android 14，MyOS 14.5.33。
- 原神界面语言：中文。

## 交付范围

先交付供用户在基准手机上安装验证的自用 APK，包含必要的权限引导、启停和诊断能力。公开发布、应用更新机制和广泛机型支持留待验证通过后讨论。

## 已确认行为

- 玩家手动游玩时边跑边捡，自动拾取不得打断玩家移动。
- 只点击明确识别为物品拾取的提示，无法确认就跳过；接受因此发生的漏捡。
- 第一阶段以 Android 自动拾取体验为目标，不要求兼容 BetterGI 的脚本、路线和配置格式。后续路线兼容性尚未决定。
- 首版固定一套游戏显示设置和横屏方向，不要求自动适配任意布局；具体设置在真机验证时记录。
- 接受采用 MediaProjection 时，每次新建截图会话由用户手动确认录屏授权。会话被系统结束后停止拾取，等待用户重新启动。
- 启动后默认暂停，由用户进入游戏后明确开启；提供悬浮按钮随时暂停。
- 权限失效、截图中断或无法确认游戏画面时停止点击，等待用户恢复。
- 对明确识别的物品全部拾取，首版不提供黑白名单。
- 完全在手机本地运行，日常使用不依赖网络。默认不保存截图；用户主动开启诊断时才保存必要截图。

## 真机验收目标

以下是用户确认的目标，尚未执行验收，也不代表已经证明可达：

- 连续运行 30 分钟，覆盖边移动、边转视角、连续拾取。
- 自动点击造成的移动中断、需要重新落指，以及误点对话等非拾取交互均为 0 次。
- 人工标注至少 100 次符合首版范围、提示清晰可见的拾取机会，成功拾取比例至少 95%。漏识别或因无法确认而跳过也计入未成功拾取。
- 在成功拾取的样本中，至少 95% 从清晰拾取提示出现到触发点击不超过 1 秒。
- 在固定游戏设置和相同场景下，开启辅助后的游戏平均帧率相比关闭辅助时下降不超过 10%。功耗和温度同时记录，尚未设置数值门槛。
- 性能测量条件不足时，对应指标明确标记为未验证。

## 首个技术验证门槛

先验证真实触控与注入点击共存，再建设完整识别与配置功能。验证覆盖持续按住摇杆，以及摇杆加视角双指操作时的自动点击，检查停步、触点取消和需要重新落指等问题。

若验证失败，重新讨论输入路径，不降低“不打断移动”的要求。此处记录的是已确认的验证顺序，验证尚未执行。

## 待验证：真实触控与注入点击共存

无障碍服务与 Shizuku 是用户选择的权限方案，尚不代表已经解决触控共存。

[Android 无障碍接口文档](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#dispatchGesture(android.accessibilityservice.GestureDescription,%20android.accessibilityservice.AccessibilityService.GestureResultCallback,%20android.os.Handler))明确指出，派发手势会取消正在进行的手势。[Shizuku](https://github.com/RikkaApps/Shizuku-API)提供 shell/root 身份执行能力，没有保证真实触控与合成触控自动合流；[AOSP 的 input tap 实现](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/services/core/java/com/android/server/input/InputShellCommand.java)也不能作为触控共存已成立的证据。

需要在基准设备上验证持续摇杆、摇杆加视角双指操作期间的注入点击，观察是否出现停步、摇杆复位、需要重新落指或点击被忽略。验证尚未执行。
